# 計画書: PDFプレビューへのテキスト選択レイヤー追加(v1.1)

v1.0からの変更点: UI操作方針を全面変更(既定でテキスト選択を有効にし、右クリックメニューから範囲選択(クロップ)モードへ切り替える方式に変更)、プレビューの固定解像度問題への対応をスコープに追加。変更理由は末尾「v1.0からの変更理由」を参照。

## 目的

QuickMarkPDFでPDFを開いたときのプレビュー表示は、pdfiumでページ全体をビットマップ画像に焼いて`<canvas>`/`<img>`に描画しているだけで、DOM上のテキストが一切存在しない。そのため開いたPDFの種類を問わず、テキストの選択・コピー・ブラウザ内検索が原理的に不可能になっている。プレビューパネル(現在表示中の1ページ)に、pdfiumのテキスト抽出APIを使った透明なテキストレイヤーを画像の上に重ね、既定でドラッグ選択・コピーができるようにする。あわせて、プレビューの固定解像度によるズーム時のぼやけを解消し、README/仕様書にこれらの機能を反映する。

## 現状分析

- `core/native/pdf_backend.cpp`の`PdfBackend::render_page()`/`render_page_at_dpi()`(L246-348)が`FPDF_RenderPageBitmap`でページ全体をRGBA8ビットマップ化するのみで、文字位置・文字列を返す経路がない。
- `core/native/webview_main.cpp`の`handle_render_page()`(L990-1012)が`render_page`を呼び、base64ピクセルデータを`page_rendered`メッセージで返す。
- `static/js/app.js`の`page_rendered`受信ハンドラ(L1219-1230)が`paintImage()`(L413-426)でcanvas/imgにピクセルを描画し、`previewNaturalWidth/Height`(natural=ズーム前の座標系)と`currentZoom`(最大8倍)で表示サイズを決める(L752-780)。
- **プレビューは固定`PREVIEW_RENDER_WIDTH = 900`px幅でしかレンダリングされず**(L12)、ズーム(`applyPreviewZoom`)はCSSスケールのみで再レンダリングしない。A4ページ幅で約109DPI相当となり、8倍ズームすると文字の輪郭がぼやける。
- プレビュー上の**左ドラッグは既に「クロップ範囲選択」に割り当て済み**(L855-905、`#crop-overlay`)。**右ドラッグは既に「パン/ズーム」に割り当て済み**(L793-825、`wheelMode`に応じてパンかズームかが変わる)。右クリックの既定コンテキストメニューは`event.preventDefault()`で単純に抑制されているだけ(L825)で、独自メニューはまだ出していない。
- サムネイルパネル向けの右クリックメニューは既に`showContextMenu(x, y, sourcePath)`(L440-484)として実装済み(回転・PDF切り出し・画像切り出し・削除・ファイルを閉じる、の固定itemsリスト)。プレビュー用に転用するにはitemsを可変にする軽いリファクタが要る。
- pdfium SDK(`third_party/pdfium/include/fpdf_text.h`)にテキスト抽出API一式が定義されており、`third_party/pdfium/bin/pdfium.dll`のエクスポートテーブルに`FPDFText_LoadPage`/`CountChars`/`CountRects`/`GetRect`/`GetText`等が実際に存在することを`objdump -p`で確認済み。
- **Acrobat Reader/Chrome内蔵PDFビューア/pdf.js等の実装方式を確認した上での結論**: これらはいずれも「画像(埋め込みフォントのグリフをそのままベクター描画) + 透明テキストレイヤー(選択用)」の二層構造であり、代替フォントでのDOM再描画は行っていない。QuickMarkPDFがpdfiumでページ全体をラスタライズしている現行方式は、見た目に関してはこれと同じ土台であり、「文字が画像でぼやける」原因はレンダリング解像度(上記の固定900px問題)であって、テキストの表現方式そのものではない。

## 変更内容

### 1. `core/native/pdf_backend.h` / `pdf_backend.cpp`

- `PdfiumApi`構造体に`FPDFText_LoadPage`, `FPDFText_ClosePage`, `FPDFText_CountChars`, `FPDFText_CountRects`, `FPDFText_GetRect`, `FPDFText_GetText`の関数ポインタを追加し、`load_symbol`でロードする。
- 新規型を追加:
  ```cpp
  struct TextRun { double x0, y0, x1, y1; std::string text; };  // top-left-origin PDF points
  struct TextLayout { double page_width_pt; double page_height_pt; std::vector<TextRun> runs; };
  ```
- 新規静的メソッド`PdfBackend::get_text_layout(path, page_index, rotation, password = "")`を追加。処理内容:
  1. `open_source_cached`でドキュメント取得 → `LoadPage` → `SetPageRotation`(render_pageと同じ回転適用)
  2. `FPDFText_LoadPage`でテキストページを取得
  3. `FPDFText_CountChars`で総文字数を取得し、`FPDFText_CountRects(text_page, 0, char_count)`で行矩形数を取得
  4. 各矩形について`FPDFText_GetRect`で座標(PDF user space, bottom-left origin)を取得し、render_pageと同じ規則でY反転してtop-left originに変換
  5. 同じ矩形範囲のテキストを`FPDFText_GetText`で取得しUTF-8に変換
  6. `FPDFText_ClosePage`で解放し、`TextLayout`を返す

### 2. `core/native/webview_main.cpp`

- 新規WebMessage`get_text_layout`(パラメータ: `page_index`)のハンドラ`handle_get_text_layout()`を追加。`ref.source_path`/`ref.original_page_index`/`ref.rotation`を使って`PdfBackend::get_text_layout`を呼び、結果を`text_layout`メッセージ(`page_index`, `page_width_pt`, `page_height_pt`, `runs:[{x,y,w,h,text}, ...]`)として返す。失敗時はpage_renderedと同様にサイレントに諦める。
- `dispatch_test_command()`にも同名のTCPテストコマンドを追加し、QA側から矩形・文字列を直接検証できるようにする。

### 3. `static/js/app.js` -- プレビュー解像度の改善

- `PREVIEW_RENDER_WIDTH`固定900pxをやめ、`currentZoom`変更が(ホイール操作の連続中は)収まってから、実際に必要な表示解像度(`previewEl`のクライアント幅 × `currentZoom` × 端末のdevicePixelRatio、上限を設けて過大なリクエストを防ぐ)で`render_page`を再リクエストするデバウンス処理を`applyPreviewZoom()`に追加する。既存の`page_rendered`受信ハンドラ(`data.width === PREVIEW_RENDER_WIDTH`の判定、L1221)は動的な幅と比較する形に直す。
- テキストレイヤーの座標もこの再レンダリング後の`previewNaturalWidth/Height`基準で再計算する(4節で詳述)。

### 4. `static/js/app.js` -- テキスト選択レイヤー

- プレビューに現在表示中のページの`page_rendered`が届いた際、追加で`get_text_layout`をリクエストする(**サムネイルパネル向けのrender_page呼び出し(L664, L703)には適用しない**)。
- `text_layout`受信時、`#preview`内の`img`の直後に`#text-layer`(position:absolute)を生成し、各runを`span`要素として配置する:
  - `left/top/width/height`は`natural座標 * currentZoom`(既存の`renderCropOverlay`と同じ変換方式)
  - フォントサイズは矩形の高さから算出し、実測テキスト幅と矩形幅が合うよう`transform: scaleX(...)`で微調整(pdf.jsのtextLayerと同じ手法)
  - `color: transparent`, `user-select: text`, 改行防止に`white-space: pre`
- `applyPreviewZoom()`実行時に、テキストレイヤーの各spanも同時に再配置する。

### 5. `static/js/app.js` -- 操作モード切り替え(v1.1で変更)

- **既定でテキスト選択を有効にする**: `#text-layer { pointer-events: auto }`。左ドラッグは通常のブラウザテキスト選択として機能し、クロップ用の`mousedown`ハンドラ(L855)はテキスト選択モードの間は登録・発火させない。
- **右クリックのクリック(ドラッグなし)でコンテキストメニューを表示する**。既存の右ドラッグ(パン/ズーム、L793-825)と共存させるため、`mousedown(button===2)`時の座標を記録し、`mouseup(button===2)`時の移動量が閾値(5px、既存のクロップドラッグ判定 L891-893と同じ基準)以下なら「クリック」とみなしてメニューを表示し、閾値を超えていれば従来通りパン/ズームの結果を確定するだけでメニューは出さない。
- メニュー項目は現在のモードに応じて1項目だけ出す: テキスト選択モード中は「範囲選択(画像切り出し)に切り替え」、範囲選択モード中は「テキスト選択に戻す」。選択するとモードを切り替え、`#text-layer`の`pointer-events`とクロップ`mousedown`ハンドラの有効/無効を入れ替える。
- `showContextMenu()`(L440-484)の`items`引数を固定リストから可変にするリファクタを行い、サムネイル用呼び出し(L556)とプレビュー用呼び出しの両方から使えるようにする。
- モード状態は`localStorage`に保存しない(ページを開くたびテキスト選択優先の既定に戻す)。
- `static/css/style.css`にテキストレイヤー・モード表示用のスタイルを追加。

### 6. `document/spec.md` / `document/spec_jp.md`

- 機能一覧(4節)に「テキスト選択・コピー」を追加(#22)。既定で有効、右クリックメニューから範囲選択(クロップ)モードに切り替えられる旨を明記。
- WebMessageプロトコル表(5節)に`get_text_layout` / `text_layout`を追記。
- 画面構成表(3節)の「プレビュー」欄に操作モード切り替えの説明を追記。
- 9節(パフォーマンス)にプレビューの動的解像度レンダリングの挙動を追記。

### 7. `README.md` / `README_jp.md`

- 「主な機能」/「Key Features」箇条書きに、プレビューでのテキスト選択・コピー対応を1行追記。

### 対象外(変更しないもの)

- サムネイルパネルへのテキストレイヤー付与(非対象、動的解像度化も対象外)
- Markdownプレビュー側(既にDOM/HTMLなのでブラウザ標準のテキスト選択が元から機能しており対応不要)
- `HISTORY.md`/`HISTORY_jp.md`の更新(実装完了後の結果記録時に別途)

## 検証方法

- `core/native/engine_tests.cpp`(またはCLI版)に、既知のテキストを含むテストPDFに対して`get_text_layout`が期待通りの文字列・矩形数を返すユニットテストを追加し、`build_native.py`の`build_tests()`でPASSを確認する。
- `python/qa/test_api_client.py`経由のTCPテストAPIで新規`get_text_layout`コマンドを叩き、サンプルPDFに対してrunsの文字列内容を検証するQAスクリプトを追加する。
- 実機ビルド後、WebView2アプリでPDFを開き、既定状態のまま左ドラッグでテキスト選択→Ctrl+Cでクリップボードにコピーされ、メモ帳等に貼り付けて正しい文字列になることを目視確認する。
- 右クリック(ドラッグなし)でメニューが出て「範囲選択に切り替え」→以降は左ドラッグがクロップ選択として動作し、再度右クリックで「テキスト選択に戻す」が効くことを確認する。
- 右ドラッグ(パン/ズーム)の既存操作が、右クリックメニュー追加後も従来通り機能する(閾値未満のクリックとしてメニューが誤って出ない)ことを回帰確認する。
- ズーム操作後にプレビューが再レンダリングされ、8倍ズームでも文字がぼやけずシャープに表示されることを目視確認する(before/after比較)。
- 90度/270度回転させたページでもテキスト矩形が画像上の文字と一致することを目視確認する。

## リスク

- `FPDFText_CountRects`/`GetRect`が返す矩形はPDF内部のテキストオブジェクト単位でマージされるため、段組みや特殊なレイアウトでは行の区切られ方がビットマップ画像上の見た目と完全には一致しない可能性がある。
- 90/270度回転ページでの座標変換(`SetPageRotation`とY反転の組み合わせ)は`render_page`の実装と別経路で書くため、回転関連のバグが混入しやすい。engine_testsでの検証を必須とする。
- MathJaxの数式(SVGパスとして焼き込まれ、そもそもPDF内にテキストオブジェクトが存在しない)や、スキャン画像PDF(元からテキストレイヤーが無いPDF)では、この機能を入れても選択できる文字が無い(runsが空になるだけでエラーにはならない)。既知の限界として説明文書に明記する。
- 右クリックの「クリック vs ドラッグ」判定の閾値が既存のパン/ズーム操作の感度と噛み合わないと、意図せずメニューが出た/出なかったりする回帰が起きうる。
- ズーム操作の度に`render_page`を再リクエストするとホイール連続操作時に大量のIPC/レンダリングが発生しうるため、デバウンス処理の間隔調整を誤るとプレビューの追従性能が悪化するリスクがある。

## v1.0からの変更理由

- ユーザー指示: 「機能：文字は文字としてレンダリングして表示する、マウスで選択できること、マウスによる画像としての範囲選択は右クリックメニューから選択後に切り替える」を反映し、既定操作をテキスト選択優先・クロップ選択を右クリックメニュー経由の明示切替に変更(v1.0はツールバートグルボタンで既定OFFの案だった)。
- 「文字は文字としてレンダリングして表示する」の実現方式について、Acrobat Reader等の実装方式(画像+透明テキストレイヤーの二層構造であり代替フォントでのDOM再描画ではない)を確認した上でユーザーと合意し、v1.0で提案した画像+透明テキストレイヤー方式を維持しつつ、別途指摘のあった固定解像度によるズームぼやけの解消をスコープに追加した。
