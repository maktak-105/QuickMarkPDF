# 計画書: Markdown改ページ記法の対応(v1.2)

## 目的

Markdown から PDF を書き出すとき、任意の位置で改ページできるようにする。
現状は改ページ手段が一切なく、見出しをページ先頭に揃えることができない。

## 現状分析

- `src/ui/js/app.js:205` の `escapeHtml` が全ての `<` `>` をエスケープする。
  同ファイル 138〜141 行のコメントどおり、Markdown 内の生 HTML は「タグとして
  解釈せず文字として表示する」のが意図された設計。このため
  `<div style="page-break-before: always;"></div>` と書いても、PDF にその文字列が
  そのまま印字される（＝ユーザーが「効いてない」と報告した事象）。
- `page-break` / `break-before` という記述はプロジェクト全体に 0 件。改ページ機能自体が未実装。
- PDF 出力は `src/app/main_gui.cpp:1501` の WebView2 `PrintToPdf`（Chromium の印刷エンジン、
  A4 縦・余白 12mm）。DOM 側に改ページ指定の要素さえあれば Chromium が改ページする。
- 印刷用 CSS は `src/ui/css/style.css:428` の `@media print` ブロック。
- UI 一式は `scripts/bundle_html.py` が `core/native/generated_index.html` にバンドルし、
  exe に RCDATA として埋め込まれる。ビルドは `scripts\build.bat`（build.py が bundle を自動実行）。
- Python 版のソースは削除済み（`__pycache__` のみ残存）。C++ 版が唯一の実装。
- 現在 `main` ブランチ、作業ツリーはクリーン、最新は v4.1.0。

## 変更内容

### 1. `src/ui/js/app.js` — 改ページ記法の認識

`markdownToHtml` のループ内、`<hr>` 判定（290〜296 行）の直後に改ページ判定を追加する。
独立した 1 行が次のいずれかに一致したら `<div class="page-break"></div>` を出力する:

- `<div style="page-break-before: always;"></div>`
  （`page-break-after` / `break-before` / `break-after` も可。空白・引用符の揺れ、
  終了タグ省略、自己終了 `/>` も許容。大文字小文字は無視）
- `<div class="page"></div>` / `<div class="page"/>`
  （VS Code の Markdown PDF 拡張が使う記法。他ツールとの互換のため）

**生 HTML 全般は解禁しない。** 上記パターンだけをホワイトリストで拾う。
`escapeHtml` 自体には手を入れないので、それ以外の生 HTML は従来どおり文字として表示される。

### 2. `src/ui/css/style.css` — 改ページの実体

- 画面表示用: `.markdown-content .page-break` を破線 1 本で可視化し、
  どこで改ページされるか編集中に分かるようにする。
- `@media print` 内: `.markdown-content .page-break { break-before: page; }` を追加し、
  画面用の破線は印刷時に消す。

### 3. `src/ui/css/style.css` — 水平線(`---`)が印刷で見えない既存バグの修正

v1.1 の検証中に発見した、今回の変更とは無関係な既存バグ。`@media print` に `hr` の色指定が
なく、画面用の `--border-color`(`rgba(255,255,255,0.08)` = ほぼ透明な白)のまま白背景に
印刷されるため、Markdown の水平線が PDF 上でまったく見えない。v4.1.0 で表の罫線を直した際の
直し漏れ。`@media print` 内に `hr` の罫線色(#ddd 相当)を追加する。

### 変更しないもの

- `escapeHtml` の挙動（改ページ記法以外の生 HTML は従来どおりエスケープ）
- PDF 出力まわりの C++ コード（`main_gui.cpp`、ページサイズ・余白含む）
- 既存の UI・ツールバー・PDF 閲覧機能
- 改ページ記法を含まない既存 Markdown の出力結果（ページ数・レイアウトとも現状維持）

## 検証方法

1. `scripts\build.bat` が成功する。
2. `dist\QuickMarkPDF.exe` を起動し、改ページ記法入りのテスト Markdown を開く。
   - 画面プレビューに区切りの破線が出る
   - `<div ...>` の文字列が画面に出ていない
3. そのまま PDF 出力し、PDF を PNG 化して**目視確認**する。
   - 指定した位置で改ページされている
   - `<div ...>` の文字列が印字されていない
   - 文書の先頭に記法を置いた場合に空白ページが出ないこと
   - 連続指定・文書末尾指定で余計な空白ページが出ないこと
4. リグレッション: 改ページ記法を含まない既存 Markdown を出力し、
   従来と同じページ数・レイアウトであることを確認する。
5. 実データ確認: `解説集レビュー記録.md` を出力し、
   「🔴 要修正」がページ先頭に来ていることを目視する。
6. 水平線(`---`)が PDF 上で罫線として見えることを目視する。

## リスク

- `<div class="page">` を別の意図で使っている既存文書があれば、意図せず改ページされる。
  現状そのような文書は確認されていない。実害は小さいと判断。
- 先頭・末尾・連続指定で空白ページが生じる可能性 → 検証 3 で実物を見て確認する。
- ビルド時に exe がロックされて失敗する場合がある。
  その際は `QuickMarkPDF.exe` の PID だけを特定して `taskkill /PID <pid> /T /F` で終了する。
  **`msedgewebview2.exe` をプロセス名で一括終了することは絶対にしない**（Teams 等を巻き込むため）。

## v1.1 からの変更点（v1.2）

### v1.1 の実装・検証結果（確定済み）

- 実装・ビルド・検証を完了。改ページ記法 6 パターンすべてが PDF 上で改ページされ、

### 今回の追加・決定

- **空白ページの扱い: 現状のまま（ユーザー判断）**。検証の結果、改ページ記法を 2 つ連続で
  置くと空白ページが 1 枚入り、文書末尾に置くと末尾に空白ページが 1 枚出ることを確認した。
  いずれも他の Markdown→PDF ツールや Word と同じ標準的な挙動で、意図的な白ページ挿入にも使える。
  抑制はしない。
- **水平線の既存バグを今回あわせて修正する（ユーザー判断）**。上記「変更内容 3」を追加。
