# 計画書: C++/WebView2版をPython版に完全一致させる(v1.3)

v1.2からの変更点: 手書きYAMLマニフェスト方式をやめ、**Python版・C++版の両方に対して同一手法(ウィンドウ全体のスクリーンショット→UI要素ツリーの機械的走査→各要素領域を切り出してサイズ・HSVを自動計測)で全パーツを網羅的に計測する抽出器**に置き換える。計画全体を**測定→実装→再測定を繰り返すループ**として構成する(ユーザー指示によりv1.2を差し替え)。

## 目的

1. Python版の全パーツ(ウィンドウ・アイコン・サムネイル・ボタン等すべて)について、**サイズとHSVを数値で自動抽出**する
2. Python版が持つ**全機能・全操作を漏れなくリストアップ**する
3. C++版は開発の節目ごとに1.と2.の**総チェック**を実行し、進捗を管理する
4. 上記を**測定→実装→再測定のループ**として回す

## 現状分析

- Python(`python/src/pdf_editor/ui/*.py`): `QMainWindow.findChildren(QWidget)`で全ウィジェットを再帰列挙できる。各ウィジェットは`.geometry()`(ウィンドウ相対の位置・サイズ)を持つ。色はウィジェット単位の明示的なプロパティではないため、**ウィンドウ全体を`QWidget.grab()`で1枚のスクリーンショットにし、各ウィジェットの矩形でその画像を切り出して代表色(最頻色）をHSVに変換する**方式で全パーツ分を一括取得できる。操作(QAction)は`findChildren(QAction)`でショートカット・テキスト・ツールチップを自動列挙できる。ホイールズーム・右ドラッグパン・ラバーバンド選択など`QAction`化されていない操作は、ソースを読んで別途リスト化する(自動列挙できない箇所として明記する)
- C++(WebView2): CDP(`--remote-debugging-port`)経由で`DOM.getDocument`→`DOM.querySelectorAll('*')`で全DOM要素を列挙できる。`DOM.getBoxModel`で各要素の正確な矩形(px)が取れる。色はPython側と同じ方式に揃えるため、**`Page.captureScreenshot`でウィンドウ全体を1枚取得し、DOM要素の矩形でその画像を切り出して代表色をHSVに変換する**(Python側と全く同じアルゴリズム)。こうすることで両者の計測ロジックが対称になり、「片方だけ甘い計測」というチェッカー側のバグが入り込みにくくなる
- **自動化できない箇所**: PythonのウィジェットツリーとC++のDOMツリーは構造が異なる(`QToolButton`と`<button id="open-button">`など)ため、「どのPython部品とどのC++部品が対応するか」は人間が対応表(`qa/part_mapping.yaml`)として1回だけ作る必要がある。この対応表は測定結果ではなく識別のための最小限のメタデータであり、値そのもの(サイズ・HSV・機能有無)はここに書かず、すべて自動計測・自動抽出で埋める

## 変更内容

### 0. 抽出器の実装(ループの外、最初の1回)

- `qa/extract_python.py`: Python版`MainWindow`をoffscreenで構築 → `findChildren(QWidget)`で全パーツ列挙 → ウィンドウ全体`grab()` → 各パーツの矩形を切り出しサイズ(px)・代表色(HSV)を計測 → `findChildren(QAction)`で全操作(テキスト・ショートカット・有効/無効条件)を自動列挙 → ソースコードを読んでQAction化されていない操作(ズーム/パン/クロップ選択/ドラッグ&ドロップ/右クリックメニュー項目/パスワード再試行/QSettings永続化項目)を`qa/manual_behaviors.yaml`に列挙(自動化不能な箇所として明記) → 全てを`qa/baseline.json`に出力
- `qa/extract_cpp.py`: `QuickMarkPDF.exe`を`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`で起動 → CDPで全DOM要素列挙 → `Page.captureScreenshot` → 各要素の矩形を切り出しサイズ・HSVを同一アルゴリズムで計測 → `qa/part_mapping.yaml`の対応表を使ってPython側パーツ名と突き合わせ可能な形で`qa/cpp_measured.json`に出力
- `qa/part_mapping.yaml`: 人手で作成する唯一の対応表(パーツID・Python側の特定方法・C++側のCSSセレクタ)。値は書かない、対応関係のみ
- `qa/diff.py`: `baseline.json`と`cpp_measured.json`を突き合わせ、パーツごとに「サイズ完全一致か」「HSV完全一致か」「機能・操作が存在し同じ結果を返すか」を判定し、`qa/results/diff_<timestamp>.json`と合格率%を出力

### 0.5 自己証明(ループに入る前に1回)

- **再現性の証明**: `extract_python.py`をPython版に対し2回連続実行し、同一のサイズ・HSVが出ることを確認(計測自体にブレが無いことの証明)
- **チェッカーが甘くないことの証明(否定側の証明)**: 現行の、既に不一致と分かっているC++ビルド(削除/元に戻すボタンの誤追加・プレビュー背景色の不一致など)に対して`extract_cpp.py`→`diff.py`を実行し、**これらの既知の不一致が正しくFAILとして検出されること**を確認する。これに失敗する場合、チェッカーが甘い(何でもpassにしてしまう)ということなので、チェッカー側を修正してからでないとループに入らない
- 両方の証明結果を`qa/results/self_proof.json`に記録し、計画の結果記録に添付する

### 1〜4. ループ本体

自己証明が通ったら以下を**合格率100%になるまで繰り返す**:

```
LOOP:
  1. extract_cpp.py + diff.py を実行し、qa/dashboard.html を更新(パーツ別・機能別の合格率%、不一致の詳細一覧)
  2. dashboard.html の不一致一覧から未解決項目を選び、core/native/ または templates/ / static/ を修正
     (前計画のA〜K相当の内容は、この不一致一覧が自動的に列挙するため、手動でリスト管理する必要はなくなる)
  3. build_native.py でビルド
  4. 1に戻る
  終了条件: diff.py の合格率が100%(サイズ・HSV完全一致、機能・操作の欠落なし)
```

## 変更しないもの

- PDFコアロジック・ビルドスクリプトは対象外
- `qa/`配下は新規ディレクトリ。既存の`tests/`(Python自動テスト)・plans/運用には手を加えない
- `qa/part_mapping.yaml`の対応表(識別のためのメタデータ)以外、人間が値を手書きする箇所を作らない

## 検証方法

- 0.5節の自己証明(再現性・否定側の検出)が両方通ることを、ループに入るための必須条件とする
- ループの各周回で`qa/dashboard.html`の合格率%が単調に上がることを記録する(下がった場合はデグレとして即座に原因を調査する)
- 100%合格をもって「完全一致」の完了と判定する。目視・自己申告での完了報告はしない

## リスク

- スクリーンショット切り出し方式は、Qt/Chromiumのどちらもアンチエイリアスのかかったテキスト境界を含む矩形だと代表色(最頻色)がぶれる可能性がある。対策として、パーツごとに矩形の中央付近の単色領域のみをサンプリングする(境界5px程度を除外する)ロジックを`extract_*.py`双方に共通で実装し、この処理自体もPython版の自己証明(再現性チェック)で妥当性を確認する
- CDP接続の初期化タイミングは前計画同様のリスクとして残る
- `qa/part_mapping.yaml`の対応表に漏れがあると、そのパーツは「検査対象外」になり見た目上の合格率が実態より高く出る。対応表のパーツ数がPython側`findChildren`で列挙される総数と近いか(著しく少なくないか)を`diff.py`実行時に警告表示し、対応表の網羅漏れに気づけるようにする
