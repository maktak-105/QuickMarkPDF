# リポジトリ構成整理 v1.0

作成日: 2026-08-19
対象アプリ: QuickMarkPDF

## 1. 背景

QuickMarkPDFのC++/WebView2移植は、CMake + Visual Studio 2022 Build Tools(MSVC)を使い、`core/native/`(エンジン)と`core/webview2/`(WebView2ホスト)を別フォルダに分け、開発用UIは単一の`ui/`フォルダに置く構成で進めていた。

しかしワークスペース内には`C:\Users\0120025-Z100\source\project\___appli-template`という共通テンプレートリポジトリがあり、QuickFolderSize/QuickDiskBenchを含む「Quick系アプリ」全体がこのテンプレートの構成・ビルド方式・命名規則に従うことが前提になっていた。この前提は以前のセッションでユーザーから伝えられていたが、メモリに保存されておらず、本セッションでは把握していなかった。結果として、CMake+MSVC+`core/webview2/`+`ui/`という、テンプレートと異なる独自構成でここまで進めてしまっていた。

本ドキュメントは、テンプレートへ合わせるために行った変更の記録である。

## 2. テンプレートの要点(`___appli-template/01_フォルダ構成.md`)

- `core/native/` 一つにネイティブコードを全て置く(エンジン・WebView2ホスト・CLI・アイコン/リソース)。`core/webview2/`のような分離フォルダは無い
- 開発用UIは `templates/index.html` + `static/css|js|img/`。`bundle_html.py`が単一の自己完結HTMLへバンドルする。`ui/`のような単一フォルダ構成ではない
- ビルドは `build_native.py`(g++直接呼び出し)+ `build.bat`(薄いラッパー)。CMakeは使わない
- ビルド出力は `dist/binary/`(Git管理外、`.gitkeep`のみ管理)。フラット構成(サブフォルダなし)で、そのまま配布ZIPの中身になる
- ツールチェインはMinGW-w64 g++のみ。MSVC/Visual Studioは前提にしていない

## 3. 実施内容

| 項目 | Before | After |
|---|---|---|
| ビルドシステム | CMake(`core/native/CMakeLists.txt`, `core/webview2/CMakeLists.txt`) | `build_native.py` + `build.bat`(g++直接呼び出し、CMake廃止) |
| WebView2ホスト | `core/webview2/host.cpp`(MSVC専用、`Microsoft::WRL::Callback`/`ComPtr`使用) | `core/native/webview_main.cpp`(MinGW対応、自作の生COM実装) |
| 開発用UI | `ui/index.html`, `ui/app.css`, `ui/app.js` | `templates/index.html`, `static/css/style.css`, `static/js/app.js` + `bundle_html.py` |
| ビルド出力 | `core/native/build/`, `core/webview2/build/`(CMakeの生ビルドディレクトリ) | `dist/binary/`(フラット、`.gitkeep`管理) |
| アイコン/バージョン情報 | 無し | `core/native/QuickMarkPDF.ico`, `QuickMarkPDF.rc`(旧Python版の`resources/app_icon.ico`を流用) |
| 必要ツールチェイン | MinGW(native/tests) + MSVC(webview2) | MinGW-w64のみ |

## 4. WRL依存の除去について

`host.cpp`は`Microsoft::WRL::Callback<>`/`ComPtr<>`(`<wrl.h>`/`<wrl/event.h>`)でWebView2のCOMコールバックを実装していた。これがMinGWでビルドできるか、憶測ではなく実際に確認した:

```
$ g++ -std=c++17 -c wrl_test.cpp -o wrl_test.o
wrl_test.cpp:2:10: fatal error: wrl/event.h: No such file or directory
```

`<wrl.h>`自体は見つかるが`<wrl/event.h>`(`Callback<>`を提供するヘッダ)がこのMinGW-w64ディストリビューションには存在しない。つまりMSVC依存はスタイルの問題ではなく実際のビルド阻害要因だった。

対応は、ワークスペース内`QuickFolderSize/core/native/webview_main.cpp`で既に実証済みのパターンを踏襲: 3つのCOMコールバック(`EnvCompletedHandler`・`ControllerCompletedHandler`・`WebMessageReceivedHandler`)を、`std::function`をラップした自作の`IUnknown`実装に書き換えた。`CreateCoreWebView2EnvironmentWithOptions`も、`WebView2Loader.dll.lib`を直接リンクするのではなく`LoadLibraryW`/`GetProcAddress`で実行時に解決するよう変更(pdfium.dllと同じパターン)。`IFileOpenDialog`/`IShellItem`/WICインターフェースには、標準ライブラリのみで書いた最小限の`ComPtr<T>`(`std::unique_ptr`ベース)を使い、早期returnでのCOM参照リークを防いだ。
