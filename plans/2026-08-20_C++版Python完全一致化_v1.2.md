# 計画書: C++/WebView2版をPython版に完全一致させる(v1.2)

v1.1からの変更点: 色の一致判定を「近似(ΔE閾値)」から**「HSV各成分の完全一致」**に厳格化。判定対象は「見た目のある部位すべて」とし、色は開発者が指定する値である以上、レンダリングエンジンが違っても完全一致させられるという前提に立つ(ユーザー指示によりv1.1を差し替え)。

## 目的

1. Python版(仕様の正)とC++版の一致度を、人間の目視に頼らず**自動判定**できる検査プログラムを作る
2. その検査プログラムが正しく機能することを、**既存のPython版EXE自身に対して実行し100%合格することで証明**する(検査プログラム自体のバグ・甘さを排除する)
3. C++版の実装(前計画v1.0のA〜K)は、この検査プログラムを都度実行しながら進め、**進捗を%で示すダッシュボード**を生成する
4. UIの一致度は**ピクセル単位**で評価する
5. **色は全ての部位でHSV完全一致とする**(近似・許容誤差ではなく、H・S・Vの各値が一致することを合格条件とする)

## 現状分析

- Python版は`tests/`配下に既にpytest-qt基盤があり、`QT_QPA_PLATFORM=offscreen`でQMainWindowを実際に構築しウィジェットツリーを検査できる。`tests/visual/`には`QWidget.grab()`によるスクリーンショット回帰の仕組みが既にある(`tests/visual_baselines/`)
- C++版(WebView2)には現状デバッグ用の外部インターフェースが無い(`core/native/*.cpp`にCDP/remote-debugging関連のコードは無いことを確認済み)。ただしWebView2はChromiumベースであり、環境変数`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<port>`を設定するだけで、**コード変更なしに**Chrome DevTools Protocol(CDP)経由の外部接続を有効化できる。これはpostmortemが失敗した「ネイティブファイル選択ダイアログのSendKeys/UI Automation」とは全く別物(Web標準のDOM操作・スクリーンショットAPIであり、ネイティブWin32ダイアログの弱点を踏まない)
- **色のHSV完全一致をどう実現するか**: 色は開発者が明示的に指定する値(Python側は`main_window.py`/`thumbnail_panel.py`のQSS文字列中の16進カラーコード、C++側は`style.css`のCSS値)であり、フォントのアンチエイリアスのような「原理的に完全一致しえないもの」ではない。したがって色の検査は、**スクリーンショットの画素を目視相当でサンプリングするのではなく、両実装のソースが定義する色の値そのものを取得して比較する**方式にする:
  - Python側: 各ウィジェットの`styleSheet()`/`palette()`から該当プロパティの色を取得(QSSをパースするか、`QWidget.palette().color(...)`を直接読む)
  - C++側: CDPの`Runtime.evaluate`で対象DOM要素に`getComputedStyle(el).backgroundColor`等を実行し、返ってきた`rgb(r,g,b)`を取得
  - 両者をRGB→HSVに変換し、H・S・Vの整数値(0-255または0-360スケール、実装時に統一)が完全一致するかを判定する。スクリーンショットの画素サンプリングは、アイコン画像の有無など「色の一致では判定できない特徴」の補助検査としてのみ使う(6章参照)
- 両者はレンダリングエンジンが根本的に異なる(Qtネイティブウィジェット vs Chromium/HTML)ため、スクリーンショット同士の直接diffは意味のある判定にならない。上記の「定義された色の値そのものを比較する」方式であれば、レンダリングエンジンの違いに影響されず、ユーザー要求(5.)の「HSV完全一致」を字義通り満たせる

## 変更内容

### 1. 仕様マニフェスト(`qa/spec_manifest.yaml`)

Python版ソース(`main_window.py`, `thumbnail_panel.py`, `export_dialog.py`, `preferences_dialog.py`)を人間が読み、検査可能な項目を列挙してYAMLに書き出す。各項目に検査種別を付与する:

```yaml
- id: toolbar.open_button
  category: structural
  desc: "開くボタンがツールバーに存在し、アイコン+テキストを持つ"
- id: toolbar.no_delete_button
  category: structural
  desc: "削除ボタンはツールバーに存在しない(キーボードのみ)"
- id: preview.wheel_zoom
  category: behavioral
  desc: "プレビュー上でホイール操作をすると表示倍率が変わる"
- id: preview.background_color
  category: color
  desc: "プレビュー背景色のHSVがPython版と完全一致する"
  python_selector: "preview_label.styleSheet() の background-color"
  cpp_selector: "#preview の getComputedStyle().backgroundColor"
- id: thumbnail.selected_highlight_color
  category: color
  desc: "サムネイル選択時のハイライト色のHSVが完全一致する"
- id: toolbar.button_has_icon
  category: visual_feature
  desc: "ツールバーの各ボタン領域にテキストだけでなくアイコン画像が存在する(色一致では判定不能な項目の例外的な画素検査)"
  region: toolbar
```

`category`は`structural`(構造の有無)・`behavioral`(操作して状態変化を確認)・`color`(HSV完全一致、原則こちらを優先)・`visual_feature`(色比較で表現できない画素特徴、例外的にのみ使用)の4種。色で判定できるものは全て`color`カテゴリにする。全項目は前計画(v1.0)のA〜K洗い出しをベースに、Python版ソースの再読で漏れなく起こす。

### 2. Python版チェッカー(`qa/check_python.py`)

- `pytest-qt`のoffscreen基盤を使い、実際に`MainWindow`を構築してマニフェストの`structural`/`behavioral`項目をウィジェットツリー・シグナル発火で直接検査
- `color`項目は対象ウィジェットの`styleSheet()`/`palette()`から色を取得しHSVに変換
- `visual_feature`項目のみ`QWidget.grab()`でスクリーンショットを取得し画素特徴を判定
- 結果を`qa/results/python_<timestamp>.json`に出力(項目ごとpass/fail、実測HSV値、根拠)

### 3. C++版チェッカー(`qa/check_cpp.py`)

- `QuickMarkPDF.exe`を`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`付きで起動
- CDP経由で同じマニフェストを検査。`structural`はDOM要素の有無、`behavioral`は`Input.dispatchMouseEvent`/`dispatchKeyEvent`で実操作して状態変化を確認、`color`は`Runtime.evaluate`で`getComputedStyle()`を取得しHSVに変換、`visual_feature`のみ`Page.captureScreenshot`で画素検査
- 結果を`qa/results/cpp_<timestamp>.json`に同フォーマットで出力(実測HSV値も記録し、Python側の値との差分がダッシュボードで見えるようにする)

### 4. 自己検証(証明ステップ)

- `check_python.py`をPython版EXE(またはoffscreenテスト経由のMainWindow)に対して実行し、**全項目が100%合格することを確認**する。合格しない項目があれば、それはPython版のバグではなく**チェッカー側の実装ミス**とみなし、チェッカーを修正する(Python版は仕様の正であり、ここで100%にならない設計は許容しない)
- `color`項目については、Python版チェッカーが自分自身の`styleSheet()`から読み取った値と、実際にレンダリングされたウィジェットのスクリーンショットから画素サンプリングした値が一致することも合わせて確認し、「定義値と実描画が一致している」こと自体を検証する(定義値だけを見て安心しないための二重チェック)
- この結果を`qa/results/python_baseline_proof.json`として保存し、計画の結果記録に添付する

### 5. 進捗ダッシュボード(`qa/dashboard.py` → `qa/dashboard.html`)

- `check_cpp.py`の最新結果を読み込み、カテゴリ別(構造/操作/色/画素特徴)・全体の合格率%を集計
- 静的HTMLダッシュボード(`qa/dashboard.html`)を生成。項目ごとにpass/fail、`color`項目はPython側/C++側それぞれの実測HSV値を並べて表示
- C++実装(前計画A〜K)を1項目進めるたびに`check_cpp.py`→`dashboard.py`を再実行し、%が上がることを都度確認しながら進める

### 6. C++実装(前計画v1.0のA〜K)

- 上記の検査基盤ができてから着手する。各項目の「完了」は、当該マニフェスト項目がチェッカーでpassすることをもって判定する(目視・自己申告では判定しない)。`color`項目については、`static/css/style.css`の値をPython側QSSと**同一の16進カラーコード**に揃えることで機械的に満たせる

## 変更しないもの

- PDFコアロジック・ビルドスクリプトは前計画同様、対象外
- `qa/`配下は新規ディレクトリ。既存の`tests/`(Python自動テスト)・plans/運用には手を加えない

## 検証方法

- `check_python.py`実行結果が100%合格することを「証明」の合格基準とする
- `check_cpp.py`実行結果の合格率を、C++実装の完了度の唯一の指標とする(目視確認は補助情報に留め、完了の根拠にはしない)
- 色は「両実装が定義する色の値をHSVに変換して完全一致するか」で判定する(スクリーンショット同士の直接diffではない。理由: レンダリングエンジンが異なるため直接diffは無意味な基準になるが、定義値の比較であればエンジンの違いに影響されず完全一致を字義通り要求できる)

## リスク

- CDP接続はWeb標準機能でありネイティブダイアログ自動化より格段に安定するはずだが、初回接続確立・タイミング(WebView2初期化完了待ち)で詰まる可能性がある。詰まった場合はpostmortemの教訓(建前ではなく実物を都度確認)に従い、CDPの生レスポンスを都度ログに残しながら進める
- マニフェストの網羅性はPython版ソースの読み込み精度に依存する。読み漏れがあれば「100%合格=完全一致」ではなくなるため、マニフェスト自体もレビュー対象とし、新たな差分に気づいた時点で追記する(上書きでなく追記、版を上げる)
- 色のHSV完全一致は、Python版のQSS文字列とC++版のCSSの値を突き合わせて機械的に揃えれば達成できるため技術的リスクは低い。リスクがあるのは「値を取得する手段」(QSSパース・getComputedStyle)の実装ミスの方であり、4章の自己証明ステップでそこを潰す
- スコープが大きい。まず1章(マニフェスト)〜4章(自己証明)を完成させ、その時点で一度提示してから5章(ダッシュボード)・6章(C++実装再開)に進む
