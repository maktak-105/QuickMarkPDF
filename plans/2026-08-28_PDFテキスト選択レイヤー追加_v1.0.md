# 計画書: PDFプレビューへのテキスト選択レイヤー追加(v1.0)

## 目的

QuickMarkPDFでPDFを開いたときのプレビュー/サムネイル表示は、pdfiumでページ全体をビットマップ画像に焼いて`<canvas>`/`<img>`に描画しているだけで、DOM上のテキストが一切存在しない。そのため開いたPDFの種類を問わず、テキストの選択・コピー・ブラウザ内検索が原理的に不可能になっている。プレビューパネル(現在表示中の1ページ)に、pdfiumのテキスト抽出APIを使った透明なテキストレイヤーを画像の上に重ね、ドラッグ選択・コピーができるようにする。あわせてREADME/仕様書にこの機能を反映する。

## 現状分析

- `core/native/pdf_backend.cpp`の`PdfBackend::render_page()`/`render_page_at_dpi()`(L246-348)が`FPDF_RenderPageBitmap`でページ全体をRGBA8ビットマップ化するのみで、文字位置・文字列を返す経路がない。
- `core/native/webview_main.cpp`の`handle_render_page()`(L990-1012)が`render_page`を呼び、base64ピクセルデータを`page_rendered`メッセージで返す。
- `static/js/app.js`の`page_rendered`受信ハンドラ(L1219-1230)が`paintImage()`(L413-426)でcanvas/imgにピクセルを描画し、`previewNaturalWidth/Height`(natural=ズーム前の座標系)と`currentZoom`(最大8倍、CSSスケールのみで再レンダリングしない)で表示サイズを決める(L752-780)。
- プレビュー上の**左ドラッグは既に「クロップ範囲選択」に割り当て済み**(`static/js/app.js` L855-905、`#crop-overlay`)。新機能はこの既存操作と衝突しないようにする必要がある。
- pdfium SDK(`third_party/pdfium/include/fpdf_text.h`)にテキスト抽出API一式が定義されており、`third_party/pdfium/bin/pdfium.dll`のエクスポートテーブルに`FPDFText_LoadPage`/`CountChars`/`CountRects`/`GetRect`/`GetText`等が実際に存在することを`objdump -p`で確認済み(実装の前提が崩れていないことを確認済み)。
- `FPDFText_CountRects`/`GetRect`は「同じ行・同じフォント設定の文字ボックスを自動的に大きな矩形へマージする」仕様(ヘッダコメントより)で、行単位のテキストレイヤーに使うのに適している。
- `PdfBackend::render_page`は`SetPageRotation`を適用してから`GetPageWidthF/HeightF`を呼んでおり、回転後の座標系で幅・高さを得ている。テキスト矩形もこれと同じ回転適用後の座標系・Y反転(top-left origin化)で揃える必要がある。

## 変更内容

### 1. `core/native/pdf_backend.h` / `pdf_backend.cpp`

- `PdfiumApi`構造体に`FPDFText_LoadPage`, `FPDFText_ClosePage`, `FPDFText_CountChars`, `FPDFText_CountRects`, `FPDFText_GetRect`, `FPDFText_GetText`の関数ポインタを追加し、`load_symbol`でロードする。
- 新規型を追加:
  ```cpp
  struct TextRun { double x0, y0, x1, y1; std::string text; };  // top-left-origin PDF points
  struct TextLayout { double page_width_pt; double page_height_pt; std::vector<TextRun> runs; };
  ```
- 新規静的メソッド`PdfBackend::get_text_layout(path, page_index, rotation, password = "")`を追加。処理内容:
  1. `open_source_cached`でドキュメント取得 → `LoadPage` → `SetPageRotation`(render_pageと同じ回転適用)
  2. `FPDFText_LoadPage`でテキストページを取得
  3. `FPDFText_CountChars`で総文字数を取得し、`FPDFText_CountRects(text_page, 0, char_count)`で行矩形数を取得
  4. 各矩形について`FPDFText_GetRect`で座標(PDF user space, bottom-left origin)を取得し、render_pageと同じ規則でY反転してtop-left originに変換
  5. 同じ矩形範囲のテキストを`FPDFText_GetText`で取得しUTF-8に変換
  6. `FPDFText_ClosePage`で解放し、`TextLayout`を返す

### 2. `core/native/webview_main.cpp`

- 新規WebMessage`get_text_layout`(パラメータ: `page_index`)のハンドラ`handle_get_text_layout()`を追加。`ref.source_path`/`ref.original_page_index`/`ref.rotation`を使って`PdfBackend::get_text_layout`を呼び、結果を`text_layout`メッセージ(`page_index`, `page_width_pt`, `page_height_pt`, `runs:[{x,y,w,h,text}, ...]`)として返す。失敗時はpage_renderedと同様にサイレントに諦める(該当ページのテキスト選択が効かないだけにする)。
- `dispatch_test_command()`にも同名のTCPテストコマンドを追加し、QA側から矩形・文字列を直接検証できるようにする。
- `document/spec_jp.md`のWebMessageプロトコル表に準拠する形でコメント・命名を揃える。

### 3. `static/js/app.js`

- プレビューに現在表示中のページの`page_rendered`が届いた際、追加で`get_text_layout`をリクエストする(**サムネイルパネル向けのrender_page呼び出し(L664, L703)には適用しない** — 小さすぎて実用性がなく、コスト増になるだけのため対象外)。
- `text_layout`受信時、`#preview`内の`img`の直後に`#text-layer`(position:absolute)を生成し、各runを`span`要素として配置する:
  - `left/top/width/height`は`natural座標 * currentZoom`(既存の`renderCropOverlay`と同じ変換方式)
  - フォントサイズは矩形の高さから算出し、実測テキスト幅と矩形幅が合うよう`transform: scaleX(...)`で微調整(pdf.jsのtextLayerと同じ手法)
  - `color: transparent`, `user-select: text`, 改行防止に`white-space: pre`
- `currentZoom`が変わる処理(`applyZoomTransform`相当、L752-780)で、テキストレイヤーの各spanも同時に再配置する。
- **既存のクロップ選択との操作衝突対策**: メインツールバーに「テキスト選択」トグルボタンを追加する。
  - OFF(既定値): `#text-layer { pointer-events: none }` — 見た目にも影響を与えず、既存のクロップドラッグ操作は今まで通り動く
  - ON: `#text-layer { pointer-events: auto }` に切り替え、`previewEl`のクロップ用`mousedown`ハンドラ(L855以降)をこの間だけ無効化する
  - モード状態は`localStorage`に保存しない(環境設定で永続化しているホイールモードとは異なり、ページを開くたびクロップ選択優先の既定に戻す)
- `static/css/style.css`にテキストレイヤー・トグルボタン用のスタイルを追加。

### 4. `document/spec.md` / `document/spec_jp.md`

- 機能一覧(4節)に「テキスト選択・コピー」を追加(#22)。
- WebMessageプロトコル表(5節)に`get_text_layout` / `text_layout`を追記。
- 画面構成表(3節)の「プレビュー」欄にテキスト選択モードトグルの説明を追記。

### 対象外(変更しないもの)

- サムネイルパネルへのテキストレイヤー付与(非対象)
- Markdownプレビュー側(既にDOM/HTMLなのでブラウザ標準のテキスト選択が元から機能しており対応不要)
- クロップ選択のデフォルト操作性(既定OFFなので変更なし)

## 検証方法

- `core/native/engine_tests.cpp`(またはCLI版)に、既知のテキストを含むテストPDFに対して`get_text_layout`が期待通りの文字列・矩形数を返すユニットテストを追加し、`build_native.py`の`build_tests()`でPASSを確認する。
- `python/qa/test_api_client.py`経由のTCPテストAPIで新規`get_text_layout`コマンドを叩き、サンプルPDFに対してrunsの文字列内容を検証するQAスクリプトを追加する。
- 実機ビルド後、WebView2アプリでPDFを開き、「テキスト選択」トグルON→ドラッグ選択→Ctrl+Cでクリップボードにコピーされ、メモ帳等に貼り付けて正しい文字列になることを目視確認する。
- 90度/270度回転させたページでもテキスト矩形が画像上の文字と一致することを目視確認する(回転座標変換のバグが起きやすい箇所のため)。
- ズーム変更・パネルリサイズ後もテキストレイヤーの位置がずれないことを目視確認する。
- トグルOFF時、既存のクロップ範囲選択(左ドラッグ)が従来通り動作することを回帰確認する。

## リスク

- `FPDFText_CountRects`/`GetRect`が返す矩形はPDF内部のテキストオブジェクト単位でマージされるため、段組みや特殊なレイアウトでは行の区切られ方がビットマップ画像上の見た目と完全には一致しない可能性がある。
- 90/270度回転ページでの座標変換(`SetPageRotation`とY反転の組み合わせ)は`render_page`の実装と別経路で書くため、回転関連のバグが混入しやすい。engine_testsでの検証を必須とする。
- MathJaxの数式(SVGパスとして焼き込まれ、そもそもPDF内にテキストオブジェクトが存在しない)や、スキャン画像PDF(元からテキストレイヤーが無いPDF)では、この機能を入れても選択できる文字が無い(runsが空になるだけでエラーにはならない)。これは本機能の対象外であり、既知の限界として説明文書に明記する。
- テキスト選択トグルとクロップ選択の排他制御が漏れると、ドラッグ操作が意図しない方(選択 or クロップ)に取られる回帰が起きうる。
