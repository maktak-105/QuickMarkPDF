# 計画書: アプリ本体UIへの日英切替ボタン追加(v1.0)

## 目的

QuickMarkPDFのUIは現在、意図的に日本語固定(`document/spec_jp.md`に「表示言語: 日本語のみ（言語切替なし）」と明記、v1.0.0時点から一度も言語切替機能が存在しない)。アプリ本体のツールバーに、既存ボタンと同じ見た目のトグルボタンで日本語/英語を切り替えられる機能を追加する。C++側のネイティブダイアログ・ステータスメッセージも含めて完全対応する。

## 現状分析

UI文字列は3箇所にハードコードされている(`grep -cP '[日本語文字コード範囲]'`で行数集計):

- **`templates/index.html`**(約72行): メニューバー(設定/ヘルプ)、ツールバーのボタンラベル・title属性、ヘルプモーダル本文、バージョン情報モーダル、エクスポート/環境設定モーダルの全項目、welcome画面の案内文
- **`static/js/app.js`**(約94行): `setStatus(...)`によるステータスバーメッセージ、右クリックメニュー項目(`buildPageActionMenuItems`他)、Markdownレンダラのラベル等、エクスポートダイアログの動的な例文生成
- **`core/native/webview_main.cpp`**(約62行): `post_status(...)`経由でJSに送るステータスメッセージ、`MessageBoxW`/`TaskDialogIndirect`によるネイティブダイアログ(未保存変更の確認、パスワード入力、重複ファイル通知、保存方法の選択等)

`engine.cpp`には日本語文字列は無く(GUI非依存のコアロジックのため)、この計画の対象外。

既存の資産:
- ツールバーボタンは2種類のスタイルパターンを持つ: `class="tool"`(`resources/icons/`のPNGアイコン+ラベルspan)と`class="size-btn"`(テキストのみの選択式ボタン、[style.css:110-117](static/css/style.css#L110-L117)、小/中/大サムネイルサイズ切替に使用中)。言語切替用のアイコン画像は存在せず新規作成もしない方針のため、`size-btn`と同じテキストのみのパターンを踏襲する
- 設定の永続化機構が両側に既にある: JS側は`localStorage`(サムネイルサイズ・ホイールモード)、C++側は`HKEY_CURRENT_USER`配下のレジストリ([webview_main.cpp:207-271](core/native/webview_main.cpp#L207-L271)、DWORD/文字列の保存・読み込みヘルパーあり)。この2つは独立して管理されており、今回言語設定は両方に保存し、C++側の初期値はレジストリから、JS側はWebMessageでC++からもらう(またはlocalStorageと二重管理)必要がある

## 変更内容

### 1. 言語状態の管理

- **JS側**: `static/js/app.js`冒頭に`let currentLang = 'ja';`を追加。`localStorage`(`quickmarkpdf.lang`)に永続化(既存の`quickmarkpdf.thumbSize`と同じパターン)
- **C++側**: `webview_main.cpp`に`enum class Language { Japanese, English }`と`Language g_language`を追加。起動時に既存のレジストリDWORD読み込みヘルパーで`Language`キーを読み込み初期化。新規WebMessage`set_language`(パラメータ`lang`: `"ja"`/`"en"`)を追加し、JS側の切替操作のたびにC++側へ通知、`g_language`更新とレジストリ保存を行う
- 起動直後、JS初期化前に発生しうるC++側メッセージ(通常は起きないが念のため)はレジストリの値を正として扱う

### 2. 翻訳辞書とヘルパー

- **JS側**: `static/js/i18n.js`を新規作成し`bundle_html.py`に組み込み対象として追加。`const STRINGS = { ja: {...}, en: {...} }`で全UI文字列をキー管理し、`t(key, params)`ヘルパー(`{n}`のようなプレースホルダをparamsで置換)を提供する
- **HTML側**: `templates/index.html`の静的テキストに`data-i18n="key"`(textContent用)、`data-i18n-title="key"`(title属性用)等を付与。`applyLanguage()`が`document.querySelectorAll('[data-i18n]')`等を走査してテキスト/属性を差し替える。`<html lang="ja">`のlang属性もここで更新
- **app.js内の動的文字列**: `setStatus(...)`呼び出し、`buildPageActionMenuItems`のラベル、確認ダイアログ文言、エクスポート例文生成などを全て`t(key, params)`経由に置き換える
- **C++側**: `webview_main.cpp`に`std::wstring tr(TrKey key, ...)`相当のヘルパー(キーごとに日英2つのフォーマット文字列を持つテーブル)を追加。`post_status`/`MessageBoxW`/`TaskDialogIndirect`で使われている文字列リテラルを全て`tr(...)`呼び出しに置き換える

### 3. 切替ボタン

- メインツールバーの右側（保存ボタンの後、区切り線を挟む）に、`size-btn`と同じスタイルの2つの選択式ボタン(「日本語」/「English」、排他選択・現在の言語に`checked`クラス)を追加する
- クリック時: `currentLang`を更新 → `applyLanguage()`でDOM全体を再描画 → `localStorage`保存 → WebMessage `set_language`でC++側にも通知(ステータスバーの直近メッセージ・以降のダイアログ文言に反映されるようにする)

### 4. ドキュメント更新

- `document/spec.md`/`spec_jp.md`の「表示言語: 日本語のみ（言語切替なし）」を、切替対応の説明に更新
- `README.md`/`README_jp.md`の「UIは日本語のみ、言語切替はありません」的な記述を更新

### 対象外(変更しないもの)

- Markdownプレビューのユーザーコンテンツ自体（ユーザーが書いたMarkdown文章）の翻訳は対象外
- Windows標準のファイル選択ダイアログ（`GetOpenFileNameW`/`IFileDialog`）自体の言語はOS設定に従う（タイトル文字列のみ`tr()`対象、ダイアログ内のボタン等はOS標準のまま）
- `HISTORY.md`/`HISTORY_jp.md`の更新（実装完了後の結果記録時に別途）

## 検証方法

- 日英それぞれで、ツールバー・メニュー・モーダル・ヘルプ本文・バージョン情報・右クリックメニュー・ステータスメッセージ・保存確認ダイアログ・パスワード入力ダイアログ・重複ファイル通知ダイアログを一通り操作し、翻訳漏れ（日本語のまま残る文字列）がないか目視確認する
- アプリ再起動後も選択した言語が維持される（レジストリ・`localStorage`両方から復元される）ことを確認する
- `build_native.py`のビルド（GUI/CLI/engine_tests）が通ることを確認する
- 変数を含むメッセージ（「Nページを回転しました」等）が、英語表示でも自然な語順になることを確認する

## リスク

- 対象文字列が約228行相当と多く、翻訳キーの付け漏れ・対応漏れが起きやすい。特に`app.js`内の変数埋め込み文字列は、テンプレート化を誤ると英語表示が破綻する
- C++側は文字列リテラルがコード中に散らばっており、`tr()`化の際に一部を見落とす、あるいは日英のキーが対応しないコンパイルエラーが起きるリスクがある
- JS↔C++間の言語設定同期にタイミングのズレがあると、起動直後の一部メッセージだけ意図しない言語になる可能性がある
- ボタン追加によって既存メインツールバーの幅が増え、小さいウィンドウ幅でレイアウトが崩れる可能性がある
