# 計画書: C++/WebView2版をPython版に完全一致させる(v1.0)

## 目的

QuickMarkPDFのC++/WebView2版(`core/native/`, `templates/`, `static/`)を、**Python/PySide6版(`python/`、仕様の正)と機能・見た目・操作感で完全一致させる**。
これまでの検証(`plans/2026-08-20_C++*`)は個別操作の実機確認に終始し、Python版ソースとの構造比較を欠いていたため、下記の差分を「ほぼ同等」と誤って報告していた。本計画はこれを是正する。

CPP_PORT_POSTMORTEM.mdの方針を踏襲する: 「Python版と同じ見た目・同じ機能・同じ操作性を再現すること」であり、それ以外は移植とみなさない。Python版に無いUIは追加しない。

## 現状分析(Python版ソース = 仕様の正、行番号は現時点のもの)

- `python/src/pdf_editor/ui/main_window.py`: メインウィンドウ全体。QSplitter・ツールバー2段・メニューバー・プレビュー(ズーム/パン/クロップ選択)・バックグラウンド処理・QSettings永続化・パスワード再試行・未保存確認
- `python/src/pdf_editor/ui/thumbnail_panel.py`: サムネイル1枚を「通し番号ガター＋ファイル名タグ＋画像＋p.N元ページ番号」の4要素キャンバスとして自前描画、ドラッグ&ドロップ、右クリックメニュー
- `python/src/pdf_editor/ui/dialogs/export_dialog.py`: 出力対象(全/選択)・出力領域(全体/クロップ)・形式(PNG/JPEG)・DPI(72/150/300/カスタム)・JPEG品質スライダー・保存先参照・接頭辞・出力例プレビュー
- `python/src/pdf_editor/ui/dialogs/preferences_dialog.py`: ホイール動作(zoom既定/scroll)のラジオボタン

対する現行C++版:
- `templates/index.html` / `static/css/style.css` / `static/js/app.js`: 上記のほぼ全てが欠落、または簡略化。加えてPython版に無い「削除」「元に戻す」ツールバーボタンが存在する
- `core/native/webview_main.cpp` / `engine.cpp` / `pdf_backend.cpp`: PDF操作のコアロジック(回転・削除・並べ替え・保存・切り出し・画像出力)自体はエンジンテストで検証済みであり、本計画では原則対象外。設定永続化・パスワード再試行など、コアに新規追加が要るものだけ拡張する

## 変更内容

### A. 不要UIの削除(Python版に合わせて引き算)
- `templates/index.html`: ツールバーから「削除」「元に戻す」ボタンを削除。Delete/Ctrl+Zキーボードショートカットのみに統一(`static/js/app.js`に実装済みのショートカット処理は残す)

### B. 見た目の一致
- ツールバーボタンにアイコンを追加(既存の`resources/` or `python/src/pdf_editor/resources`配下のアイコン素材を流用可能か確認、無ければ同等のSVG/PNGを新規作成し`static/img/`に配置)。テキストは残しアイコン+テキストの2段構成に
- `static/css/style.css`: `.preview`の背景色を`#d8d8d8`→`#1e1e1e`、文字色を明るいグレーに変更(Python版`main_window.py`のPreviewLabelスタイルに合わせる)
- サムネイルパネル/プレビュー間の境界をCSS Gridの固定幅からリサイズ可能な分割(ドラッグハンドル)に変更。JSでドラッグ操作を実装(`static/js/app.js`)
- サムネイル1枚の描画を、Python版と同じ4要素構成(左ガターに文書内通し番号、上部にファイル名タグ、中央に画像、下部に`p.N`元ページ番号)に合わせる(`static/css/style.css` + `static/js/app.js`のレンダリング処理)

### C. プレビューのインタラクション(現在ゼロなので新規実装)
- `static/js/app.js`: プレビュー`<img>`をラップするコンテナに対し、ホイールでズーム(zoom既定モード)、右ドラッグでパン、左ドラッグでクロップ範囲のラバーバンド選択を実装。選択範囲は画像出力時のクロップに使う(`handle_export_images`へ座標を渡す。`core/native/webview_main.cpp`にクロップ範囲を受け取るハンドラ追加)
- 初期表示時は幅フィット(`_fit_to_width`相当)をJSで再現

### D. 設定メニュー・環境設定ダイアログ・永続化
- `templates/index.html`: メニューバー(または相当のUI)に「設定」→「環境設定...」を追加
- 環境設定ダイアログ(ホイール動作: zoom/scroll)をHTML/CSSのモーダルとして新規実装、`static/js/app.js`にロジック追加
- 永続化(ウィンドウジオメトリ・最終使用フォルダ・サムネイルサイズ・ホイールモード): WebView2にはQSettings相当が無いため、`core/native/webview_main.cpp`側でレジストリ(`HKCU\Software\maktak-105\QuickMarkPDF`、Python版の`QSettings("maktak-105", "QuickMarkPDF")`と同じ組織名/アプリ名)への読み書きを実装し、起動時にJS側へ初期値をpostする

### E. ExportDialogの完全実装
- 現行の簡易Yes/No確認を廃止し、HTML/CSSモーダルで置き換え: 出力対象(全/選択、件数表示)・出力領域(全体/クロップ、クロップ未選択時は無効化)・形式(PNG/JPEG)・DPI(72/150/300/カスタム、カスタム時は数値入力)・JPEG品質スライダー(60-100、JPEG選択時のみ有効)・保存先(テキスト+参照ボタンでフォルダ選択ダイアログ)・接頭辞・出力例のライブプレビュー(`{prefix}_0001.{ext}`形式)
- `core/native/webview_main.cpp`: `handle_export_images`をこの詳細設定を受け取る形に拡張

### F. パスワード保護PDFの再試行
- `core/native/pdf_backend.cpp`/`engine.cpp`: 現状のパスワード処理を確認の上、開けなかった場合にJS側へパスワード入力を促すメッセージを送り、最大3回まで再試行するフローを`static/js/app.js`+`webview_main.cpp`に実装(Python版`_retry_password_protected_files`と同じ回数・文言)

### G. 複数ファイル処理の厳密化
- 複数PDF読み込み時、既に読み込み済みのファイルをスキップし、スキップしたファイル名を通知するダイアログを追加
- PDF/Markdown混在選択時に「同時読み込みは未対応、どちらか一方を選んでください」という警告を表示し中断
- 複数Markdown選択時は「先頭の1件を読み込みます」と通知した上で1件目のみ読み込む

### H. バックグラウンド処理
- 読み込み/保存/エクスポート中、Python版同様ツールバー・サムネイル・プレビューを無効化し、処理中メッセージをステータスバーに表示。WebView2はUIスレッドがブロックされると操作不能になるため、`core/native/webview_main.cpp`側で重い処理(PDF読み込み・保存・エクスポート)をワーカースレッドに逃がし、完了をWebMessageでJSへ通知する形に変更

### I. 未保存変更時の終了確認
- ウィンドウクローズ時、未保存の変更があれば確認ダイアログを表示してから終了する処理を`webview_main.cpp`に追加(Python版`closeEvent`相当)

### J. 既存の未確認項目の解消
- 右クリックメニュー「このファイルを閉じる」の実機クリック確認(座標推定の問題を回避する形で再挑戦。前回失敗した自動クリックではなく、確実な代替手段を検討)

### K. サムネイルサイズ切替
- ツールバー2段目に「サムネ / 小 / 中 / 大」を追加し、Python版と同じ3段階のサイズ切替をJS側で実装

## 変更しないもの

- PDFコアロジック(回転・削除・並べ替え・保存・PDF切り出し・PNG/JPEG画像出力の演算部分)は既存エンジンテスト(36件)で検証済みのため、原則変更しない。設定永続化・パスワード再試行など新規に必要な箇所のみ拡張する
- Markdownレンダラ(`markdownToHtml()`)の CommonMard非準拠・Mermaid/MathJax・GFMテーブル・ネストリスト対応は本計画のスコープ外(別途計画書で対応)
- ビルドスクリプト(`build_native.py`)・SDK取得スクリプトは変更しない

## 検証方法

各項目ごとに以下を満たしてから「完了」と記録する(postmortemの教訓により、ビルド成功・自動テストPASSのみでは完了と認めない):

1. `build_native.py`でビルド成功、既存エンジンテストが引き続き全件PASS
2. 実機でPowerShellの`System.Drawing`スクリーンショット+目視確認、または独立したツール(PyMuPDF/Pillow)によるファイル検証
3. **Python版のソースコードと該当箇所を直接見比べ**、見た目・挙動が一致していることを確認(今回の反省点)
4. 差分が残る場合は「完了」と書かず、残課題として明記する

## リスク

- WebView2側でのバックグラウンドスレッド化は、UIスレッドとの同期(WebMessage経由)にバグを作り込みやすい。前回のpostmortemで指摘された`EventRegistrationToken`・`OleInitialize`系の既知の落とし穴を再確認しながら進める
- レジストリへの設定永続化は、C++版で新規のOS API呼び出しが増えるため、権限・エラーハンドリングを慎重に扱う
- スコープが大きいため、一度に全て実装せず、本計画書内のA〜Kの順で段階的に実装・都度実機確認する。ただし計画書自体は分割しない(ユーザー指示により一本化)
